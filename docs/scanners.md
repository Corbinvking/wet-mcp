# W.E.T. Scanners

A scanner is a saved, structured research filter inside a user's W.E.T. account. It is not a recommendation, signal, trading bot, venue action, or order-routing instruction. A match means only that an event satisfied the stored criteria at the recorded W.E.T. board observation.

The v0.5 lifecycle becomes available only after database migration `0032_scanner_lifecycle` is applied. Before that migration, legacy reads can remain available and are explicitly labeled `legacy-pre-0032`; every lifecycle mutation, including deletion, returns typed `schema_pending`. The scheduled scanner tick also returns `schemaPending` with zero due-row reads, run-history writes, firing-memory changes, or legacy deliveries. A client or worker must never fall back to older create, update, pause, resume, run, or immediate-delete semantics.

## Preview, authorize, then create

1. Call `wet_scanner_templates`. The response distinguishes the six playbook high-intent templates from generic starters. A template whose required data is not stored is returned as `unavailable` with a reason and remedy; clients must not approximate it.
2. Translate the user's request into explicit structured criteria and call `wet_preview_scanner`.
3. Show the normalized definition and current cached-board matches. Ask the user to authorize creation.
4. Call `wet_create_scanner` once with a caller-generated `idempotencyKey`.
5. Return the immutable mutation receipt, revision receipt, stored criteria, and secret-free `useThisScannerUrl`.

Opening `/mcp/scanner-template?template=...` only decodes and validates the bounded public template payload. It shows a preview and MCP creation arguments; it never creates a scanner automatically. The link contains the normalized public definition, schedule, timezone, and deduplication window only. It contains no user, account, scanner, email, API-key, OAuth, venue-credential, wallet, or notification-secret fields.

Create and update require idempotency keys, which are stored only as SHA-256 digests. Reusing a key with the same normalized request replays the original receipt; reusing it with a different request returns a typed conflict. Keys and digests are not returned in receipts or logs. A create replay is resolved before the account capacity check, and distinct creates serialize that check, so retries remain truthful at the limit. `wet_update_scanner` also requires `expectedRevision`, so a stale concurrent update cannot overwrite a newer revision. An identical update returns a truthful no-op receipt without inventing a second immutable revision, and an exact repeated no-op reuses that receipt. Fresh valid create/update requests and state-changing resumes consume a fail-closed per-account storage-growth budget; exact idempotency replays remain free, while pause and delete remain available as unconditional stop controls.

## Test versus persisted run-now

`wet_test_scanner` is a non-persisting preview. It reads the current cached board but does not send, reserve deduplication keys, update firing memory, advance a schedule, or create a history row. It can test a paused scanner.

`wet_run_scanner` is a real persisted execution. It uses the stored lifecycle revision, records a full run row and match evidence, updates firing memory, applies deduplication, and enqueues configured delivery. A run based on a superseded revision cannot overwrite the newer scanner state or send its results. If the scanner is paused, run-now records a paused outcome and does not deliver; use `wet_test_scanner` to inspect it without resuming.

A claimed run is a 10-minute lease, and one scanner can hold only one live execution lease across scheduled and manual calls. An accepted claimant reloads the scanner state captured under that ordering before evaluation. If a worker dies after the history claim, the next execution at or after the boundary marks the abandoned row `worker_crash_recovered`, clears its scheduled-generation claim, releases only event reservations carrying that run id, and retries the same generation. State writes, event reservations, and delivery commits require an unexpired owned lease, so a slow old worker cannot later overwrite or deliver after recovery. Before the lease expires, a competing worker reports the existing claim rather than duplicating work, including when the configured post-delivery deduplication window is zero.

`wet_scanner_status` returns bounded recent run history, including the evaluated revision, outcome, trigger, observation generation and time, normalized criteria, matched-event evidence, match reasons, delivery state, and typed failure or supersession detail. Delivery payloads and receipts are field-whitelisted and contain no destination address or credential.

## Scheduling, expiry, deduplication, and delivery

- Schedules support validated intervals and daily wall-clock times in an IANA timezone. Daily scheduling observes daylight-saving transitions. If expiry is before the first valid slot, the scanner has no next run and is not treated as immediately due.
- Expired scanners do not evaluate or deliver. Pause and resume preserve firing memory; repeating an already-achieved state is a no-op.
- New-event delivery is protected by an atomic scanner/event reservation with a bounded expiry. Concurrent runs cannot both claim the same event. A failed run releases its reservations when safe; an uncertain post-side-effect failure is retained for review rather than silently duplicating delivery.
- `inApp` delivery is stored in W.E.T. notification state. `accountEmail` uses the authenticated account email only and is accepted only with the durable delivery outbox. The scanner definition, receipts, run evidence, and outbox never store or expose an email address.
- Scanner alert email has its own atomic, fail-closed daily provider budget (25 by default against a 100-message allowance), reserving 75 messages for interactive sign-in. Operators may change the three explicit capacity values together; an unavailable budget store delays alerts rather than allowing an unmetered burst.
- Firing memory, complete run evidence, the in-app receipt, email outbox intent, and the next-run clock commit in one revision-locked database transaction. A failure before that commit cannot silently advance memory without a durable delivery intent.
- Email attempts are retried from the durable outbox with one stable, server-generated provider idempotency key per outbox row. Before every attempt, W.E.T. rechecks account ownership, scanner revision, paused state, natural expiry, and source-rights policy. Stale, paused, expired, or deleted-scanner entries are cancelled rather than sent. The final eligibility check, bounded provider call, and success/failure reconciliation hold the scanner row as a database mutation lease, so update, pause, confirmed delete, and account erasure cannot win between that check and provider acceptance. Timeout/network-class failures are conservatively recorded as `provider_outcome_uncertain` with `mayHaveBeenAccepted: true`, including while still retryable. Every failed or crash-recovery row is barred from retry at a conservative 23-hour deadline anchored to immutable outbox creation (which is no later than its first provider call), and the deadline is rechecked under the outbox lease immediately before network I/O. This cannot outlive the provider's 24-hour idempotency guarantee.
- The delivery transaction is authoritative even if the immediate outbox flush fails afterward. The run-now result still reports the committed run/in-app truth and returns bounded `deliveryPending` plus `deliveryErrorCode` state; it never turns a committed scanner delivery intent into a generic “no change made” failure. The durable worker can finish the queued email later.

Every delivered alert is bounded and includes the exact normalized criteria, schedule and timezone, why each returned event matched, a W.E.T. event link, board generation and observation timestamp, and volume value/unit or an explicit refusal. Because this release evaluates the cached W.E.T. board, it states `refreshedLive: false` and explicitly marks live quote basis/quality as unavailable instead of inventing venue quotes.

## Deletion and account erasure

Scanner deletion is always two-step and server-enforced. The first `wet_delete_scanner` call returns a short-lived confirmation challenge. Only a second call with that exact challenge can delete the scanner; the challenge is stored as a digest, expires, is scanner-specific, and is consumed once. Missing, stale, or wrong confirmation never falls back to immediate deletion.

Per-scanner deletion is a tombstone, not immediate audit erasure: it stops future runs but retains the current definition, immutable revisions and distinct mutation receipts until account erasure. Run/match evidence is bounded to 30 days and the newest 1,000 rows per scanner, whichever is smaller. An incomplete live lease and a run linked to a queued, sending, or failed email intent are retained until recovery or terminalization makes deletion safe. Idempotency rows purge after 24 hours, deduplication reservations at their configured expiry, and terminal email outbox/provider-receipt metadata after 30 days; the outbox never contains the recipient address. A user can delete an individual in-app receipt. Account deletion hard-deletes all remaining scanner outbox entries, deduplication reservations, idempotency records, mutation receipts, run history, revision history, scanner rows, and in-app deliveries in dependency order.

## Source-rights hold

Production currently returns route-wide HTTP `503`/`mcp_release_held` before any public or account tool. In a controlled candidate environment, default-deny public policy `mcp-source-rights/2026-09-05.phase1` makes six sourced public tools return `source_rights_pending`, while caller-supplied `wet_resolve` is the sole public tool-level exception.

Fourteen source-derived account tools independently return `account_output_contract_pending` for v0.5.0. Their raw definitions do not yet publish the recursively closed output schemas required for a contract, so no approval can activate them in this release. A future release must add closed schemas and runtime projection, version and SHA-256 pin every tool contract, obtain separate approval, and pass authenticated production proof. Public venue grants cannot unlock that contract. Scanner evaluation and delivery additionally require the combined venue and publisher/feed headline rights chains because a saved definition can use the headline-derived `catalyst` leaf; venue grants alone cannot unlock scheduled evaluation, run-now execution, or a queued scanner email while news rights remain pending. This scanner boundary does not change the narrower venue-only gate for public tools whose output cannot contain headlines. API keys, OAuth credentials, or venue credentials cannot bypass either hold. The scheduler reports a fleet-level typed hold, leaves scanners due, does not advance firing memory, and does not write source-derived match history.

Rights-safe stop controls that do not read or deliver sourced market data remain available: pause and the server-enforced two-step deletion flow. Resume is held because it reactivates sourced evaluation. Never put venue credentials, wallets, order actions, notification secrets, or free-form executable instructions in scanner criteria.
